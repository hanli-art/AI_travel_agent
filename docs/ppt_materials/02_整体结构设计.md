# 模块二：项目的整体结构设计（15%）

> 目标：让评委相信这个项目**不是一堆脚本堆在一起**，而是有清晰分层、清晰职责边界、可扩展的工程结构。
> 建议 3-4 页：技术选型 → 四层架构 → 多智能体协作 → 一次请求的完整链路。

## 建议的页面划分

### 第 1 页｜技术选型与理由

**表格呈现（一页讲完，重点讲"为什么选它"）**

| 层次 | 选型 | 为什么选它 |
|---|---|---|
| 前端 | 原生 HTML + CSS + JS | 项目重点是智能体技术，前端刻意保持零框架、零构建，降低理解成本 |
| 后端 | FastAPI | 原生异步 `async/await`，配合智能体的异步工具调用；自动生成接口文档；轻量 |
| 智能体框架 | openai-agents SDK | 用 `@function_tool` 装饰器即可把普通函数变成工具；`handoff` 原生支持多智能体交接 |
| 数据校验 | Pydantic | 把大模型输出的自由文本变成**类型安全的结构化对象**，是工具参数与返回值的"守门员" |
| 大模型 | 通义千问（DashScope OpenAI 兼容接口） | 兼容 OpenAI 协议，可直接用 openai-agents 接入 |
| 数据源 | 高德开放平台 + 聚合数据 | 提供地理编码、驾车路径、POI、天气、火车票、航班等真实数据 |

**可补充讲框架对比（作为"我们做过调研"的证据）**

| 框架 | 核心特点 | 适用场景 | 学习曲线 |
|---|---|---|---|
| LangChain | 生态最成熟，组件最丰富 | 通用 Agent 开发 | 中等 |
| AutoGen | 多 Agent 协作强大 | 复杂协作任务 | 较高 |
| CrewAI | 角色扮演、流程化 | 团队协作模拟 | 较低 |
| Dify | 可视化编排 | 快速原型和业务 | 低 |
| **openai-agents** | **精简的 Agent 开发方法** | **轻量级、快速搭建业务** | **较低** |

**结论一句话**：
> 本项目是教学级项目，选型原则是「简单高效、易吸收」，openai-agents 能用最少代码搭出多智能体协作，最合适。

### 第 2 页｜四层架构（核心图，建议放大画满一页）

```
┌─────────────────────────────────────────────────────────────────┐
│  浏览器（index.html + static/css + static/js）                    │
│  聊天式界面：左侧会话栏（新建/切换） + 右侧消息区（Markdown 渲染）  │
└────────────────────────────┬────────────────────────────────────┘
                             │  POST /chat  {message, user_id, session_id}
┌────────────────────────────▼────────────────────────────────────┐
│  接入层  main.py（FastAPI）                                       │
│  · SQLiteSession 按 session_id 隔离多会话上下文（data/conversations.db）│
│  · MonitorHooks 监控钩子，控制台打印 Agent/Tool 执行过程            │
└────────────────────────────┬────────────────────────────────────┘
                             │  Runner.run(main_agent, ...)
┌────────────────────────────▼────────────────────────────────────┐
│  智能体层  Agent_com/                                             │
│          main_agent（总控，负责意图识别 + handoff 分发）            │
│   ┌──────────┬──────────┬──────────┬──────────┐                  │
│   │route_agent│weather_  │hotel_    │traffic_  │                  │
│   │ 路线规划  │agent天气 │agent酒店 │agent交通 │                  │
│   ├──────────┼──────────┼──────────┼──────────┤                  │
│   │food_agent│budget_   │itinerary_agent（多日行程编排）            │
│   │ 美食推荐  │agent预算 │          │          │                  │
│   └──────────┴──────────┴──────────┴──────────┘                  │
│   每个 Agent = 中文 instructions（角色与规则） + tools（能力）      │
└────────────────────────────┬────────────────────────────────────┘
                             │  调用 skill 层方法
┌────────────────────────────▼────────────────────────────────────┐
│  技能层  skill/                                                   │
│  route_skill / weather_skill / hotel_skill / traffic_skill        │
│  food_skill / budget_skill / itinerary_skill                      │
│  职责：封装一类业务能力的调用编排，不关心底层 API 细节               │
└────────────────────────────┬────────────────────────────────────┘
                             │  调用 MCP 工具
┌────────────────────────────▼────────────────────────────────────┐
│  MCP 工具层  mcp_tools/                                           │
│  · amap_mcp.py：GeomMCP / WeatherMCP / RoutePlanMCP /             │
│                 HotelSearchMCP / FoodSearchMCP                    │
│  · juhe_mcp.py：TrainMCP / FlightMCP                              │
│  · schemas.py / routeSchemas.py / itinerarySchemas.py（Pydantic 模型）│
│  职责：请求外部 API + 数据清洗 → 输出干净的结构化模型                 │
└────────────────────────────┬────────────────────────────────────┘
                             │  HTTPS
              高德开放平台 Web API      +      聚合数据（火车/航班）
```

**讲这张图的三个重点（务必说出来）**：
1. **职责单一，逐层收敛**：Agent 只管"怎么问"，Skill 管"怎么编排"，MCP 管"怎么取数和清洗"。换数据源只改 MCP 层，上层不动。
2. **数据向前收敛成结构化模型**：外部 API 的脏 JSON 在 MCP 层就被 Pydantic 模型清洗为固定字段，模型拿到的永远是干净数据。
3. **分层是可验证的**：每一层都有独立的验收脚本，可以单独测试。

### 第 3 页｜多智能体协作机制：Handoff 交接

**核心概念（用类比讲，评委秒懂）**：
> 像医院分诊台。分诊 Agent 接待用户，判断属于哪个科室，把会话控制权完整交给专科 Agent；
> 专科 Agent 接手后自己调工具、自己回复，分诊 Agent 退出，不再参与后续对话。

**技术本质（一句话点透）**：
> Handoff 本质是一次特殊的"工具调用"：SDK 自动生成 `transfer_to_xxx_agent` 虚拟工具，
> 模型判断需要转交时调用它，Runner 捕获后不执行普通函数，而是切换当前活跃 Agent。

**本项目的总控分发规则（可做成一张小表）**

| 用户意图 | 分发到 |
|---|---|
| 多日行程（「从A到B N天N夜」「帮我排个行程」） | `itinerary_agent`（一次串联路线→天气→酒店→美食→预算） |
| 路线规划 | `route_agent` |
| 天气查询 | `weather_agent` |
| 酒店住宿 | `hotel_agent` |
| 机票/火车票 | `traffic_agent` |
| 美食推荐 | `food_agent` |
| 预算计算 | `budget_agent` |

**为什么"多日行程"要单独做一个 Agent**：
> 因为真实需求是"一句话要全部"，如果让用户依次问 5 次，体验就断了。
> `itinerary_agent` 的价值在于**把多个子能力编排成一个完整交付物**，这也是本项目从"查数据"
> 走向"解决问题"的关键一步。

### 第 4 页｜一次请求的完整链路（时序图）

以「从福州自驾到杭州 6 天 5 夜，2 个人」为例：

```
用户输入
  │
  ▼
main.py /chat
  │  ① 按 session_id 取出该会话的历史上下文（SQLiteSession）
  ▼
main_agent 总控
  │  ② 意图识别：「多日行程」→ handoff
  ▼
itinerary_agent → ItinerarySkill.plan_itinerary()
  │
  ├─③ RouteSkill → RoutePlanMCP → 高德驾车路径规划
  │     得到：611km / 7.3h / 过路费 237 元 / 途经城市 / 4 个分段 / 沿途景点
  │
  ├─④ 分段映射到天：每段 1 天，剩余天数按驾驶时长插为「停留日」
  │
  ├─⑤ 每天的城市：用 pass_cities 按累计里程比例插值（不是从分段名截取）
  │
  ├─⑥ 按城市并行取数（同城结果缓存，避免重复请求）
  │     · WeatherMCP  → 该城未来 4 天预报
  │     · HotelSkill  → 该城真实酒店 POI
  │     · FoodSkill   → 该城真实餐厅 POI
  │
  ├─⑦ 汇总当日费用：门票解析 + 油费（0.6 元/km）+ 过路费按里程分摊
  │
  └─⑧ BudgetSkill → 汇总交通/酒店/美食/门票 → 总预算/人均/日均/占比
  │
  ▼
ItineraryOutput（结构化模型）
  │  ⑨ 模型把它组织成中文 Markdown 逐日行程
  ▼
前端渲染（表格 + 列表 + 引用块）
```

**这一页要强调的一个设计点**：
> 第 ⑤ 步是整个项目里最容易被忽略、但最影响正确性的一步。我们一开始就是在这里出的错，
> 具体留到第 4 模块讲（**埋一个伏笔，让心得部分自然衔接**）。
