### 第 2 页｜模块一：路线规划（技术含量最高的取数模块）

**难点不在调接口，而在"把高德的脏数据洗干净"**

高德驾车接口返回的是原始 `steps` 数组，特点是：
- 分段极碎（一次跨省自驾可能返回上百个 step）
- 途经城市只出现在 `step.cities`，而 `route.cities` 恒为空
- `path.tolls`（过路费）恒返回 `"0"`，拿不到真实金额
- `road` 字段多是隧道名、枢纽名，不是道路类型

**我们的清洗策略**

| 问题 | 处理方式 |
|---|---|
| 分段过碎 | `aggregate_steps()` 按里程与道路类型聚合为大段 |
| 途经城市为空 | 从 `step.cities` 提取去重，得到有序途经城市 |
| 过路费为 0 | 用 `toll_distance × 0.45` 估算，并在输出里注明是估算 |
| 道路类型误判 | 结合 `instruction` 文本判断（`road` 多为隧道/枢纽名） |
| 景点错位 | 按 `types=110000`（风景名胜）检索，按城市就位挂载 |

**输出模型（Pydantic 清洗后的干净结构）**

```python
class SimplifyDriveRoute(BaseModel):
    origin: str                    # 出发地名称+地址
    destination: str               # 目的地名称+地址
    pass_cities: List[str]         # 全程途经主要城市（有序）
    total_distance_km: int
    total_drive_hours: float
    total_toll_fee: int
    route_strategy: str
    has_mountain_road: bool
    daily_segments: List[RouteDaySegment]   # 聚合后的分段
    global_tips: List[str]
```

**验收证据（现场可展示）**

```
真实路线：福建省福州市福州飞南路86号 → 浙江省杭州市雷峰塔
总里程 约 601 km / 总驾驶时长 约 7.2 h / 预估过路费 ¥237（估算）
途经城市 7 座：福州市 → 宁德市 → 温州市 → 丽水市 → 金华市 → 绍兴市 → 杭州市
分段 4~5 段（而非上百段），并提示全程 111 处隧道（杭州段 64 处）
```

### 第 3 页｜模块二：天气查询（一个被踩过的坑）

**技术要点：天气接口只认 adcode，不认经纬度**

这是本项目最典型的"接口参数陷阱"：

| 错误做法 | 后果 |
|---|---|
| 把地理编码返回的**经纬度**当 `city` 传给天气接口 | 接口报错，天气查不到 |
| `address` 传空字符串去查地理编码 | 高德返回 `INVALID_PARAMS` |

**正确链路**

```
城市名（如"杭州"）
   │  GeomMCP.get_adcode(city, address)
   │  · address 为空时回退用城市名当地址（否则 INVALID_PARAMS）
   ▼
adcode（如 330106）
   │  WeatherMCP.execute(city, address, extensions)
   │  · extensions=base → 实时天气，数据在 lives
   │  · extensions=all  → 未来预报，数据在 forecasts[0].casts
   ▼
AmapWeatherResponse（Pydantic 校验整个响应体）
```

**关键代码（真实实现）**

```python
async def execute(self, city: str, address: str = "", extensions: str = "base"):
    """extensions: base=实时天气(lives)，all=未来预报(forecasts)"""
    adcode = await GeomMCP.get_adcode(city, address)
    res = requests.get(url, params={"key": AMAP_KEY, "city": adcode,
                                    "extensions": extensions}).json()
    if res.get("status") == "1":
        return AmapWeatherResponse.model_validate(res)   # 校验整个响应
```

**验收证据**

```
杭州（adcode=330106）实时天气：返回真实天气/温度/风向/湿度/发布时间
大理未来 3 天预报：forecasts[0].casts 返回逐日白天夜间天气与温度
```
> 对应脚本：`tests/p4_weather_verify.py`

### 第 4 页｜模块三、四：酒店与美食（POI 搜索 + 一个重要的数据伦理问题）

**实现方式（两者结构一致，接口不同）**

| | 酒店 | 美食 |
|---|---|---|
| 接口 | `/v3/place/around`（周边搜索） | `/v3/place/text`（关键词搜索） |
| 中心点 | 先地理编码取参考点（如"西湖"），再按中心点搜周边 | 按城市 + 菜系关键词 |
| POI 编码 | `types=100000`（住宿服务） | `types=050000`（餐饮服务） |
| 返回字段 | 名称/地址/参考价/评分/距离 | 名称/地址/人均/菜系/评分 |

> 小知识：`060000` 是"购物服务"不是餐饮，是最容易写错的编码，本项目专门验证过。

**必须讲的一个问题：高德多数 POI 不提供价格**

这是真实的数据现状，也是我们做的一个**有态度的技术决策**：

- 高德酒店 POI 的 `biz_ext.cost`（挂牌价）**大多为空**
- 景点门票 `ticket_price` 大多数返回"未知"

**我们的处理原则：宁缺勿编**

```python
price: Optional[int] = Field(default=None, ...)   # 拿不到就是 None
```
1. Schema 里价格字段改为**可选**，拿不到就是 `None`，不填 0、不猜
2. 输出统一提示「**价格需预订时确认**」「**以实际消费为准**」
3. 预算计算时，缺报价的项**不计入总额**，并明确告知"实际花费可能更高"

**验收证据**

```
杭州西湖附近 300-800 元：返回 5 家真实酒店（名称/评分/地址）
  · 仅"量子小院"有 327 元报价，其余标注"价格需预订时确认"
杭州 杭帮菜 人均 100 元内：返回 5 家真实餐厅
  · 赵府私厨 ¥66（评分4.7）· 四灶儿 ¥79 · 新周记 ¥81 · 人均区间 66-94 元
```

### 第 5 页｜模块五：交通票务（聚合数据的两个"没想到"）

**实现：火车 + 航班两个独立工具**

聚合数据**按接口分配 appkey**，一个接口一个 key，不是账号级共用一个：

```
.env 配置（两个独立 key）
JUHE_TRAIN_KEY=...    # 火车订票查询 接口ID 817
JUHE_FLIGHT_KEY=...   # 航班订票查询 接口ID 818
```

| | 火车 | 航班 |
|---|---|---|
| 接口 | `apis.juhe.cn/fapigw/train/query` | `apis.juhe.cn/flight/query` |
| 关键参数 | `search_type` / `departure_station` / `arrival_station` / `date` | `departure` / `arrival` / `departureDate` / `maxSegments` |
| 单位 | **站点名**（杭州东，不是杭州） | **IATA 三字码**（HGH/BJS，不是城市名） |
| 限制 | 仅支持未来 15 天内 | — |

**踩坑记录（讲出来很加分）**

| 坑 | 处理 |
|---|---|
| 一个接口一个 appkey，共用一个 key 会鉴权失败 | 拆成 `JUHE_TRAIN_KEY` / `JUHE_FLIGHT_KEY`，各自缺失时才回退到通用 `JUHE_KEY` |
| 航班接口要 IATA 三字码，用户只会说城市名 | 工具内部做「城市名 → IATA 三字码」映射 |
| 火车接口只认站点名，用户说"杭州" | 传入后由接口侧兼容，同时在参数说明里给出示例（如"杭州东"） |
| 票价字段结构不统一 | 做兼容解析，按席别输出为「二等座 ¥281」形式 |
| 免费额度有限 | 验收脚本严格只调 1 次，避免浪费额度 |

### 第 6 页｜模块六：预算计算（纯计算，但设计有讲究）

**特点：不调用任何外部 API，纯本地汇总**——因为它是"最后一公里"，必须稳。

**输出模型**

```python
class BudgetSearchOutput(BaseModel):
    total_cost: int                  # 总预算
    people: int
    per_person_cost: float           # 人均
    daily_average: Optional[float]   # 日均（提供天数时才有）
    breakdown: List[BudgetBreakdownItem]   # 各项费用 + 占比，按金额降序
    missing_items: List[str]         # 用户未提供的费用项
    suggest: Optional[str]
```

**三个设计细节（体现严谨性）**

1. **成本项全部设为可选**：用户没提供的费用项**不按 0 计入**，否则会严重低估总预算；
   未提供的项记入 `missing_items` 并在建议里明确提示。
2. **占比以总预算为分母**，总预算为 0 时不做除法（避免除零异常）。
3. **人数兜底**：人数未知默认按 1 人算，并提醒用户。

**验收证据**

```
场景1（四项齐全，2人4天）：1200+1600+900+500 = 4200 元
  人均 2100 元，日均 1050 元
  占比：酒店 38.1% / 交通 28.6% / 美食 21.4% / 门票 11.9%（合计 100%）
场景2（只给交通800+酒店1200）：总预算 2000，人均按 1 人兜底
  缺失项标注：美食、景点门票 → 提示"实际总预算可能更高"
```

### 第 7 页｜模块七：多日行程编排（本项目的"集大成"）

**这是把 7 个能力串成一条交付物的模块，也是技术难度最高的一页。**

**核心问题一：路线分段怎么映射到"天"？**

高德返回的是**地理分段**（4-5 段），但用户要的是"6 天"。两者数量不匹配。

```
我们的算法：
① 每个分段先各占 1 天
② 剩余天数（6 - 5 = 1 天）按"驾驶时长从长到短"依次插入，作为"停留日"
   → 驾驶最累的那天后面安排休整，符合真实旅行逻辑
③ 分段数 > 天数时：按顺序均匀合并，保证天数连续
```

**核心问题二：一天在哪个城市？**

这是**我们踩过的最隐蔽的一个坑**，直接在模块四展开讲。这里的结论是：

> 路线分段的 `section_name` 是**路口/枢纽名**（如「福州 → 南外环路」「东坑互通 → 杭州」），
> **不是城市名**。所在城市必须用 `pass_cities`（有序途经城市）按**累计里程比例**插值得到。

```python
@staticmethod
def pick_city(pass_cities: List[str], cumulative_km: int, total_km: int) -> str:
    """按累计里程占全程的比例，把当天终点映射到途经城市列表中的城市"""
    ratio = min(max(cumulative_km / total_km, 0.0), 1.0)
    return pass_cities[round(ratio * (len(pass_cities) - 1))]
```

**核心问题三：按城市并行取数 + 缓存**

- 天气/酒店/餐饮都按"城市"查询，同城只查一次（`weather_cache` / `hotel_cache` / `food_cache`）
- 6 天行程涉及 3-4 个城市，缓存把接口调用次数从 18 次降到 9 次左右

**每日费用口径（如实标注，不美化）**

| 项 | 口径 |
|---|---|
| 交通 | 油费 0.6 元/公里 + 高德预估过路费按里程分摊 |
| 门票 | 解析景点门票文本；"免费"记 0，"未知"记为 None（不计入总额） |
| 住宿 | 优先取有报价且最便宜的一家；无报价则不计入并提示 |
| 餐饮 | 取人均最低的一家 × 人数 |

**验收证据**

```
「福州 → 杭州 6天5夜，2人」
总览：611 km / 7.3 h / 过路费 237 元 / 策略"速度最快"
第1天 温州市（211km/2.5h）住宿 温州铂金酒店(评分4.9)
      餐饮 新东山海鲜 ¥148 · 宽马记大排档 ¥90
第4天 丽水市（12km/0.3h）住宿 蚂蚁电竞公寓(评分5.0)
第5天 杭州市（357km/3.9h）住宿 暖寓公寓(评分4.9)
```
