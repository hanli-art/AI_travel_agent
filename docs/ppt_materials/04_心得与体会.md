> 这是分值最高的模块（占一半）。评委在这里看的不是"你做了什么"，而是**"你想明白了什么"**。
> 下面 7 页全部来自本项目的真实经历，请按自己的语言重述，**不要照读**——照读会显得很空。

## 建议的页面划分

### 第 1 页｜心得总览（一页抓人，建议用 5 条短句）

在页面上竖排 5 条，每条一行，配一个序号：

1. **大模型有知识但没有手脚**——智能体的真正工作量在"执行"和"记忆"两件事上。

5. **架构的价值不在画出来的那一刻，而在你改代码的那一刻。**

**口播引导语**：
> 下面我想讲几个这个项目里真正让我改变认知的地方，不是技术点罗列，是我们踩过的坑。

### 第 2 页｜认知一：智能体的核心工作量，在"手脚"和"记忆"上

**技术文档里有一句话我一开始没当回事，做完才真正理解**：

> Agent = 大模型（大脑）+ 工具（手脚）+ 记忆（经验）+ 规划（智慧）

拆成四层看：

| 层次 | 内容 | 我们的工作量感受 |
|---|---|---|
| 感知层 | 用户输入 → LLM 理解 | 几乎为零，框架包了 |
| 认知层 | 推理、规划 | 对开发者是黑盒，不用管 |
| **执行层** | 工具（搜索、API 调用） | **主要工作量在这里** |
| **记忆层** | 短期/长期记忆、会话隔离 | **另一块主要工作量在这里** |

**我的体会**：
> 刚开始我以为做智能体就是"写好提示词"，后来发现提示词只是敲门砖。
> 真正的工作是：把 7 个外部接口封装成模型能安全调用的工具（执行层），
> 以及让每个用户的多轮对话互不串味（记忆层，我们用的是 SQLiteSession 按 session_id 隔离）。
> **提示词决定它想得对不对，工具和记忆决定它做不做得到。**

### 第 3 页｜认知二（最重要）：最危险的 bug，是不报错的 bug ★

**请重点讲这一页，这是整个汇报最有说服力的故事。**

**事情经过**：

做多日行程编排（P9）时，程序第一次运行**完全成功**，没有任何异常，输出了一份漂亮的 6 天行程。

但是我看了一眼结果，觉得不对：

```
第 1 天 到达 南外环路
  餐饮：新京熹·北京涮肉(白塔寺店) 174元
  餐饮：新荣记(金融街店) 454元
```

**一个"福州 → 杭州"的自驾行程，为什么推荐了北京的餐厅？**

**排错过程**：

| 步骤 | 发现 |
|---|---|
| 1. 先怀疑模型 | 但数据是工具返回的，模型只是转述，不是模型编的 |
| 2. 打印工具入参 | 发现查酒店/餐饮时传的城市是「**南外环路**」「排头隧道」「东坑互通」 |
| 3. 追问为什么 | 这些名字来自高德路线的 `section_name`，我**想当然地认为它的格式是"城市 → 城市"** |
| 4. 打印真实返回 | 实际格式是「福州 → 南外环路」「东坑互通 → 杭州」——**是路口/枢纽名，不是城市名** |
| 5. 为什么没报错 | 高德 POI 接口收到无效城市名后，**没有报错，而是回退到了默认城市**，于是返回了北京的餐厅 |

**根因**：我把"分段节点名"当成了"城市名"。程序每一步都是"合法"的，所以它不报错。

**修复**：改用路线返回的 `pass_cities`（有序途经城市列表），按**累计里程比例**插值出当天所在城市。

```
修复前：到达"南外环路" → 查餐厅 → 返回北京餐厅（错）
修复后：到达"温州市"   → 查餐厅 → 温州铂金酒店、新东山海鲜（对）
```

**我的三点体会（这是这一页的价值所在）**：

1. **对外部数据的格式，任何"想当然"都是 bug 的来源**。我假设了 `section_name` 是城市对，
   但它其实是任意节点对。**假设没有经过验证，就等同于错误。**
2. **上游"静默容错"会掩盖下游的错误**。高德对无效城市不报错而是给默认值，
   这种"宽容"让我的 bug 一直潜伏到结果层面才暴露。**上游越宽容，自己越要严格校验。**
3. **验收标准不能是"跑通"，必须是"结果符合业务常识"**。
   从那以后，我每跑完一个功能都会先问自己一句：**这个结果，讲得通吗？**
   也是从这次开始，我在验收脚本里不只是断言"有返回"，而是打印出来逐条目视检查。

> **这一页的核心金句（建议单独做成大字）**：
> **程序不报错，不代表结果是错的；只代表错得更隐蔽。**

### 第 4 页｜认知三：从"照着文档写"到"直连接口验一遍"

这个项目里，我们几乎每个外部接口都踩过坑，而且**代码看起来都很正常**：

| 踩的坑 | 真实原因 | 后果 |
|---|---|---|
| 天气智能体完全不工作 | 用了不存在的接口路径 `/v3/weather/now` | 整个模块不可用 |
| 天气查不到数据 | 把地理编码返回的**经纬度**当城市参数传（天气接口只认 adcode） | 接口报错 |
| 解析天气崩溃 | 从 `res["now"]` 取数据，但响应里根本没有 `now` 字段 | 校验必失败 |
| 地理编码报 `INVALID_PARAMS` | `address` 传了空字符串（高德要求 address 非空） | 查不到坐标 |
| 路线规划的起点终点为空时报错 | 同一个空地址问题，两个方法都中招 | 路线规划失败 |
| 酒店搜索直接抛异常 | 期望返回里有 `geocode` 字段，但周边搜索接口没有这个字段 | KeyError |
| 酒店搜索参数被忽略 | `price_min/price_max/stay_days` 根本不是高德的合法参数 | 筛选无效 |
| 火车/航班一直鉴权失败 | 以为一个账号一个 key，实际是**一个接口一个 appkey** | 两个接口都调不通 |

**共同点**：**这些都是"照着文档或想象写代码"导致的，而不是"照着真实返回写"。**

**我的体会与做法改变**：

> 后来我形成了一个习惯：**写封装之前，先用最小脚本直连打一次真实接口，把原始 JSON 完整打印出来。**
> 看清楚它到底返回什么字段、字段是什么类型、边界情况返回什么，然后再写 Pydantic 模型去清洗。
>
> 顺序很重要：**先看真实数据，再定义数据结构**，而不是反过来先写模型再指望接口配合。
> 这个项目大量的时间不是在"写功能"，而是在"确认外部系统的真实行为"——这可能是真实工程和课堂练习最大的区别。

### 第 5 页｜认知四：数据缺失时，我们选择诚实

**遇到的问题**：

- 高德酒店 POI 的挂牌价字段（`biz_ext.cost`）**大多数是空的**
- 景点门票价格**大多数返回"未知"**

也就是说，在"住宿"和"门票"这两个占比最大的花费项上，我们**拿不到可靠报价**。

**当时的诱惑很直接**：让大模型"估个大概价格"，PPT 和演示都会好看很多，预算表也能填满。

**我们的选择**：**不编造。**

| 做法 | 具体实现 |
|---|---|
| 数据模型层 | 把价格字段改为**可选**（`Optional[int]`），拿不到就是 `None`，绝不填 0 或猜测值 |
| 输出层 | 统一提示「**价格需预订时确认**」「以实际消费为准」 |
| 预算层 | 缺报价的费用项**不计入总额**，同时明确告知"实际花费可能更高" |
| 提示词层 | 在 instructions 里明确写死：**工具返回价格为空时不要编造价格** |

**我的体会**：

> 这是我这个项目里最有价值的一个决定，虽然它让我们的演示数据"不够漂亮"。
>
> 我意识到：在 AI 应用里，**"看起来完整"和"诚实"经常是冲突的**，而且冲突的时候特别难拒绝，
> 因为大模型太擅长把缺失的信息补得像真的了。
>
> 但旅游规划是要拿去做真实消费决策的。如果用户按我们编的价格去订酒店，
> 到了发现贵一倍，那这个产品就失去了最基本的信任。**旅游规划里最贵的就是"错误的价格"。**
>
> 技术能力让"编得像"变得前所未有的容易，所以**克制**反而成了更重要的能力。

### 第 6 页｜认知五：一半的坑，不在代码里

有些问题查代码永远查不出来：

| 现象 | 真实原因 | 教训 |
|---|---|---|
| 改完 `.env` 配置，代码却像没生效一样 | uvicorn 的 `reload` 只监听 `.py` 文件，**不监听 `.env`** | 配置改动必须重启服务，否则会误判成代码 bug |
| 服务一直启动不起来 / 环境被占用 | 在智能体会话里**后台常驻**启动服务，导致进程挂住 | 长驻服务应该在独立终端手动启动，工具只跑短命令 |
| 火车和航班都调不通 | **一个接口一个 appkey** 的认知偏差 | 先确认"账号级配置还是接口级配置"再动手 |

**我的体会**：

> 我一开始的排错顺序是"先怀疑代码"，结果在这类问题上绕了很久。
> 后来我改成：**先确认环境和配置的"新鲜度"（服务是不是重启过、配置是不是真的加载了），再怀疑代码。**
>
> 还有一个更实际的感受：**"我以为是 A"和"实际是 B"之间的差距，几乎全部要靠"打印出来看一眼"来消除。**
> 不管是外部接口返回、环境变量，还是中间结果——**不要推测，要观测。**

### 第 7 页｜方法论沉淀 + 不足与改进

**这个项目沉淀下来的三条方法（可以直接作为结论页）**

1. **契约先行**：用 Pydantic 把每个工具的入参和返回值定义成明确的数据契约。
   好处是——模型填错参数会被校验拦住，外部接口返回脏数据会被清洗成固定字段。
   **我们不是在"写逻辑"，而是在"定义边界"，然后让模型在边界内自由发挥。**

2. **分段交付、每段留证**：把项目拆成 P1~P9 共 9 个阶段，**每个阶段一次提交 + 一份验收脚本**。
   好处是——某个阶段的 bug 不会污染其他阶段；出问题能精确回滚；汇报时每一步都有证据可展示。
   **验收不是最后补的，它是交付物的一部分。**

3. **分层是为了"改的时候"**：Agent / Skill / MCP 三层分开，一开始画图时觉得是形式主义，
   直到修 P9 那个城市映射 bug 时才发现——**我只改了 `itinerary_skill.py` 里的一个函数，其他层一行没动。**
   架构的价值，在修改时才兑现。

**项目的不足（主动说，比被问出来好）**

| 不足 | 说明 | 改进方向 |
|---|---|---|
| 住宿/门票报价缺失 | 高德多数 POI 不提供挂牌价，导致预算偏保守 | 接入有明确报价的数据源，或让用户手动补录 |
| 沿途景点偶尔跨城 | 景点挂载在路线层，出现"12km 的路段下列出百公里外景点" | 按到分段的地理距离做二次过滤 |
| 行程不可微调 | 只能整体生成，无法"换掉这家酒店" | 增加局部重排能力，保留用户偏好 |
| 展示形式偏文字 | 逐日行程是 Markdown 表格 | 做成会话内的结构化行程卡片 |

**结尾收束（建议单独一页或放在最后一行）**：

> 这个项目最大的收获，不是我们做出了一个能跑的旅游助手，
> 而是我们第一次真切地体会到：**让 AI 接入真实世界，比让 AI 会说话难得多。**
> 真实世界的数据是脏的、是缺的、是不按文档来的——
> 而我们做的全部工作，本质上就是在**真实世界和模型之间，修一条可靠的路。**

## 答辩预案（评委可能追问，提前准备答案）

| 可能的问题 | 回答要点 |
|---|---|
| 这些数据是真实调用的吗？ | 是。可以现场跑 `tests/p9_itinerary_verify.py --full`，输出的是当天的真实路线、天气和 POI；所有 key 走 `.env`，代码里不含任何伪造数据。 |
| 为什么不做"思考过程展示"？ | 经确认前端只渲染最终回复。但我们保留了 `MonitorHooks`，控制台能看到完整的 Agent/Tool 调用链，调试时很有用。 |
| 为什么要单独做一个 itinerary_agent？ | 真实需求是"一句话要全部"。如果让用户依次问 5 次，体验就断了。它的价值是把多个子能力编排成一个完整交付物。 |
| 价格拿不到，这个预算还有意义吗？ | 有意义。我们把"能确定的"算准（交通、餐饮），把"不能确定的"明确标注出来，并提示实际会更高——**一个诚实的不完整，好过一个完整但不真实的数字。** |
| 这个项目最难的地方是什么？ | 不是写代码，是"确认外部接口的真实行为"。比如高德的分段名其实是枢纽名——这个坑不报错，只能靠对结果的业务常识判断。 |
